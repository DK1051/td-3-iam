# T3-S02 — 3H engine core (HR feed → create / move / disable, idempotent)

Repo: td-3-iam · Environment: td-3-iam · Day: D2 · Time box: 120 minutes · Credit cap: $12

## Goal
Build the core of the 3H lifecycle engine: a Python program that reads an HR feed of joiners (new staff), movers (staff changing role) and leavers (staff who left), works out what has to change, and applies it to Keycloak (an open-source identity server, used here as a stand-in for a corporate directory such as Microsoft Entra) through its Admin REST API. Service accounts (accounts used by programs, not people) are created as Keycloak clients with an owner, a purpose and an expiry date. The engine must be **idempotent**: running it twice with the same feed changes nothing the second time. The identity-proofing gate, separation-of-duties rules and attestation come in T3-S03.

1. Director: read the brief; `chores` runs `probe` and appends to `docs/PROBES.md`. Propose the plan in Plan mode (folder layout, data model, test strategy); wait for approval.
2. Director: start the local Keycloak dev server in the background and wait for it:
   `nohup env KC_BOOTSTRAP_ADMIN_USERNAME=admin KC_BOOTSTRAP_ADMIN_PASSWORD=dev-only-not-secret /opt/keycloak/bin/kc.sh start-dev --http-port=8080 > /tmp/keycloak.log 2>&1 &` (its log is `/tmp/keycloak.log`)

The password is a documented throwaway for a local test server that is deleted with the session; it is never reused anywhere.
3. `chores`: create the layout: `3h-lifecycle/README.md`, `hr/hr-feed.csv`, `hr/service-accounts.csv`, `roles-map.yaml`, `lifecycle/__init__.py`, `lifecycle/feed.py`, `lifecycle/kc.py`, `lifecycle/engine.py`, `lifecycle/__main__.py`, `scripts/keycloak-dev.sh`, `tests/unit/`, `tests/integration/`, and a repo-root `pyproject.toml` with `[tool.pytest.ini_options]` (`testpaths = ["3h-lifecycle/tests"]`, `pythonpath = ["3h-lifecycle"]`, marker `keycloak: needs a running Keycloak at localhost:8080`; test file basenames must be unique across the repo) and `[tool.ruff]` (`target-version = "py312"`, `line-length = 100`).
4. `chores`: fill `hr/hr-feed.csv` with 12 fictional Maple Harbour rows, columns exactly:
   `employee_id,action,first_name,last_name,email,department,job_title,manager_id,start_date,end_date,requested_by,approved_by,id_checked_live_video,references_contacted,education_verified`
   — 6 joiners (all three verification columns `true`; the gate that blocks unverified joiners is T3-S03 work, so this session's sample feed must not contain an unverified joiner), 3 movers (department or job change), 3 leavers (with `end_date`). Emails end in `@mapleharbour.example`; `requested_by` / `approved_by` are employee IDs of two different managers. `hr/service-accounts.csv` with 4 rows: `client_id,owner,purpose,expires_on` (one expiring within 30 days, one already expired, two healthy; owners are employee IDs from the feed).
5. `builder`: `roles-map.yaml` — department and job title → Keycloak groups (for example `department: finance` → `finance`, `job_title: Payments Officer` → `payments-initiate`, `job_title: Finance Manager` → `payments-approve`, `job_title: IT Administrator` → `privileged`), plus the realm-level role `manager` for anyone who appears as somebody's `manager_id` (seeded by `keycloak-dev.sh` only; the engine never assigns realm roles).
6. `builder`: `scripts/keycloak-dev.sh` — creates realm `maple-harbour`, the groups named in `roles-map.yaml`, the realm role `manager`, allows custom user attributes (see caveats), and seeds the eight **pre-existing** staff accounts that the feed acts on (the 3 movers in their old groups, the 3 leavers enabled, and the two managers named in `manager_id`/`approved_by` with role `manager`), using the bundled `/opt/keycloak/bin/kcadm.sh` (`kcadm.sh config credentials --server http://localhost:8080 --realm master --user admin --password dev-only-not-secret`, then `kcadm.sh create realms -s realm=maple-harbour -s enabled=true`, `kcadm.sh create groups -r maple-harbour -s name=…`, `kcadm.sh create roles -r maple-harbour -s name=manager`, `kcadm.sh create users -r maple-harbour -s username=… -s enabled=true`). Must be re-runnable (ignore "already exists"). The script reads the password from `KC_ADMIN_PASSWORD` with the throwaway as default; it never prints tokens.
7. `builder`: `lifecycle/feed.py` — parse and validate the CSV into dataclasses (`Joiner`, `Mover`, `Leaver`, `ServiceAccount`); booleans parsed strictly (`true`/`false` only); a bad row raises a clear error naming the row and column.
8. `builder`: `lifecycle/kc.py` — a thin Keycloak Admin REST client on `httpx` with one class and these calls only: get an admin token (`POST /realms/master/protocol/openid-connect/token`, `grant_type=password`, `client_id=admin-cli`), `get_user_by_username`, `create_user`, `update_user` (enabled flag, attributes `employee_id`, `department`, `job_title`, `manager_id`, `disabled_on`), `list_groups`, `user_groups`, `add_user_to_group`, `remove_user_from_group`, `get_client_by_client_id`, `create_client`, `update_client` (attributes `owner`, `purpose`, `expires_on`). Base URL and credentials come from environment variables `KC_URL` (default `http://localhost:8080`), `KC_ADMIN_USER` (default `admin`), `KC_ADMIN_PASSWORD` (default `dev-only-not-secret`). The token is kept in memory only and never logged. Before relying on any endpoint path, confirm it against the running server (an unauthenticated `GET /admin/realms/maple-harbour/users` must return 401, not 404).
9. `builder`: `lifecycle/engine.py` — two phases: `plan(feed, state) -> list[Action]` computes the difference between the feed and the current Keycloak state (create user, add/remove group, disable user, create/update client) and `apply(actions)` executes it. Rules: joiner → create user (enabled, groups from `roles-map.yaml`, attributes set); mover → group membership made equal to the map for the new department/title (add missing, remove stale), attributes updated; leaver → `enabled=false` and attribute `disabled_on=<end_date>`, memberships kept for evidence, never deleted; a mover or leaver whose account does not exist → `SKIPPED unknown user <employee_id>` in the plan (reported, never auto-created); service account → client with `serviceAccountsEnabled=true`, `publicClient=false`, `standardFlowEnabled=false`, attributes from the CSV. A second `plan` over the same feed must return an empty list. CLI (run from the repo root with `PYTHONPATH=3h-lifecycle` in front, as every command in this repo's README is written): `PYTHONPATH=3h-lifecycle python -m lifecycle plan --feed 3h-lifecycle/hr/hr-feed.csv --service-accounts 3h-lifecycle/hr/service-accounts.csv --realm maple-harbour` prints the plan as a table and changes nothing; `python -m lifecycle apply …` executes and prints a count per action type; `--dry-run` is accepted on `apply` and behaves like `plan`.
10. `builder`: tests. Unit and integration tests read committed copies `3h-lifecycle/tests/fixtures/feed-v1.csv` and `service-accounts-v1.csv`, never `hr/hr-feed.csv`, so later sessions can extend the live feed without breaking them. `tests/unit/` uses an in-memory fake with the same method names as `kc.py` (no network): feed parsing (good file; bad boolean; missing column), plan for each action type, idempotency (`plan` after `apply` is empty), leaver is disabled not deleted, mover's stale group is removed, service-account attributes round-trip. `tests/integration/` is marked `@pytest.mark.keycloak` and skipped automatically unless `GET http://localhost:8080/realms/master` returns 200 (a `conftest.py` fixture does the check with a 2-second timeout): run `keycloak-dev.sh`, `apply` the sample feed, assert the users, groups, disabled flag and clients in Keycloak, then `apply` again and assert zero actions.
11. `builder`: run `ruff check .`, `pytest -q` (unit only, as CI will), then `pytest -q -m keycloak` with the server up. Paste the three result lines into the README "Results" section.
12. `builder`: `3h-lifecycle/README.md` — what it does (plain English, with the joiner/mover/leaver and idempotent terms explained), how to run (Keycloak start command, `keycloak-dev.sh`, plan, apply), what Eojin did vs what Claude did, results, limits (no proofing gate, SoD or attestation until T3-S03; dev server only; the password is a documented throwaway). Update the repo `README.md` 3H row to "Core engine built (T3-S02); gate, SoD and attestation in T3-S03".

## Known caveats
- The environment script downloads Keycloak **26.8.1** (confirmed on GitHub releases on Oct 22). If a download fails, `probe` shows `keycloak: not installed`: run `probe` once more, then record a caveat.
- Keycloak 24 and later ignore custom user attributes unless the realm's user profile allows "unmanaged attributes" or declares them. `keycloak-dev.sh` must enable this on the `maple-harbour` realm (expected: `PUT /admin/realms/maple-harbour/users/profile` with `"unmanagedAttributePolicy": "ENABLED"` — `TODO(verify)` exact body; check the admin console's Realm settings → General → Unmanaged attributes if unsure). Client attributes are not affected.
- The bootstrap admin variables `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD` apply to Keycloak 26+; older releases used `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD`.
- The dev server stores everything in memory-backed dev files under `/opt/keycloak/data`; the cloud session is ephemeral, so every session that needs Keycloak starts it again and re-runs `keycloak-dev.sh` plus `apply`.
- Port 8080 must be free; nothing else in this repo uses it.
- Integration tests cannot run in GitHub Actions (no Keycloak there); CI covers unit tests only — say so in the README.
