## 1. Review findings

No secrets, no unsafe patterns, and no unaddressed mid-review comment. Two edge-case bugs were found. Neither is reached by the sample data and neither is covered by an acceptance criterion. Both fail safe (access stays off), but each contradicts something the README says.

- **F1 (low-medium, attestation correctness).** `engine.read_state` looks up the `manager_id` of joiners and movers, but not of leavers. If a manager's only direct report in the feed is a leaver, `attest` reports that manager as unknown. The leaver lands in `unassigned.md` as `manager E1009 is not in the directory` (scratch probe: E1009 seeded and enabled, `e1009 in state.users: False`), and that manager gets no attestation file. Cheap fix: add the leavers' `manager_id` to the ids that `read_state` looks up, plus one unit test.
- **F2 (low, availability, fail closed).** A joiner whose account is already enabled before their start date is switched off by a `disable_user` action, which writes `pending_start` last. If the logout or the consent deletion fails, the marker is never written. Every later run then treats the account as "disabled by a person". The probe showed `SKIPPED joiner E2004: account exists but is disabled (needs review before a re-hire)` both on the next run and after the start date. The joiner is never enabled automatically. This contradicts the README line "a half-finished job is simply redone by the next run", which holds only for leavers. Sessions are still ended on retry (the END_SESSIONS path), so there is no security gap. Fix it, or record a one-line caveat and README limit.
- Nits (judgement, no action needed):
  - `unassigned.md` rows always read "manager has left - reassign …", even when the reason in brackets is "has not started yet" or "is not in the directory". README line 110-111 says the same about the `plan` WARNING line, but the code prints `has not started yet` or `not found` for those cases.
  - The SOD-3 disable summary says the account "stays off until someone takes ownership". In fact it stays off until a person re-enables it (the integration test proves this, on purpose).
  - CSV values that contain `|` would break the Markdown tables. The input is a trusted HR file, so the risk is low.
  - The README "Eojin decided" list does not name the malformed-row decision (AI-USE.md and CAVEATS do).
  - `docs/RUN-SHEET.md` already says `DONE (PR #5)` before the PR exists. The REST API lists only PRs #1-#4. Confirm the number when the PR is opened.
- Secrets in tests (code check): `test_3h_controls.py` creates a random per-run password (`secrets.token_urlsafe`) and reads a client secret into memory. Neither is printed, and the assertions compare only status codes. My integration log has 0 matches for `eyJ`.
