### New findings from this review (none blocks an AC)

- **F1 (should, design asymmetry).** A service account that an administrator disabled is **switched back on** at the next run if its `expires_on` is still in the future. `_plan_service_account` sets `enabled = not expired`, and any difference from that becomes an `update_client`. People accounts are protected from this: an admin-disabled user is reported `SKIPPED` and never re-enabled. For clients the README describes re-enabling only as the case where "the owner extends the date". In practice, a client that someone disabled during an incident would quietly come back. This needs Eojin's decision in T3-S03, for example a marker such as `disabled_by_engine`, or never re-enabling at all.
- **F2 (minor).** A joiner whose account already exists **enabled** while the start date is still in the future (for example created by hand) is not disabled. Only attribute and group drift is fixed.
- **F3 (minor).** A mover whose account is disabled (for example a former leaver) still gets the group changes and stays disabled. There is no `SKIPPED` or note line for this case.
- **F4 (minor, CI risk; not tested here).** `tests/unit/test_3h_kcclient.py:11` has `TOKEN = "super-secret-token-value"`. Its Shannon entropy is 3.57, just above gitleaks' generic-api-key threshold of 3.5. Gitleaks is not installed in this session, so I could not run it. Newer gitleaks versions allowlist values made only of letters and hyphens, so it will probably pass; the CI `gitleaks` job will tell. If it flags the line, rename the value or add a `gitleaks:allow` comment.
- **F5 (minor).** `docs/RUN-SHEET.md` already says `DONE (PR #4)` before the PR exists. Confirm the number at wrap.
- No secrets, no tenant or object IDs, and no code that deletes users. Error messages hide ids (`{id}`) and never include response bodies (unit-tested). Every HTTP path I used against the live server was valid; the unauthenticated `GET /admin/realms/maple-harbour/users` returned `401`, not 404.
