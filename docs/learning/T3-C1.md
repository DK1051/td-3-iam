## Terms explained

- **Joiner, mover, leaver:** the three life-cycle events for a person: someone starts, changes role, or leaves.
- **Keycloak:** an open-source identity server that handles logins and user accounts.
- **Directory:** the database of users that an identity system keeps.
- **Group:** a named set of users that receives the same access.
- **Managed group:** a group that the lifecycle tool controls, so it can add and remove members.
- **Idempotent:** safe to repeat. A second run changes nothing once the first run has succeeded.
- **Identity proofing:** checks that a new person really is who they claim to be before access is granted.
- **Separation of duties (SoD):** a rule that no single person may hold two roles that together allow a risky action.
- **Service account:** an account used by a program or job, not by a person.
- **Client (in Keycloak):** an application that is allowed to use Keycloak for logins.
- **Attestation:** a signed statement by a manager that a person's access is still needed.
- **Environment variable:** a named value set outside the code, for example in the operating system, so that secrets stay out of files.
- **REST API:** a web interface that a program calls with plain HTTP requests.
- **Realm:** a separate tenant or namespace inside Keycloak.
- **Role:** a named permission that can be given to users or groups.
- **Token:** a short string that proves a program is allowed to call an API.
- **Unit test vs integration test:** a unit test checks one piece of code in isolation, usually with fakes; an integration test runs against the real system.

## Interview

One question at a time, graded 0 to 2. Each entry gives the question, Eojin's answer (summarised in his words), the grade, and the correction.

**Q1. Why plan first, then apply? Name one thing that goes wrong with row-by-row processing.**
- Answer: errors can be logged and fixed later; without a plan, mistakes are more likely.
- Grade: 1.
- Correction: the answer is too vague. A plan lets you check everything before touching anything: preview the changes, handle leavers first, and check separation of duties across the whole file. With row-by-row processing, if row 40 of 80 breaks the file, Keycloak is left half-changed.

**Q2. Why must apply be idempotent? Give a real case where a feed is sent twice.**
- Answer: "I don't remember what idempotent is."
- Grade: 0.
- Correction: idempotent means safe to repeat; a second run changes nothing. For example, HR's nightly export fails and is re-sent the next morning, or the job crashes and is re-run.

**Q3. Why disable a leaver instead of deleting the account? Name two things lost on delete.**
- Answer: the entire history of the leaver; then "IDK".
- Grade: 1.
- Correction: the record is evidence for later fraud investigations and audits. Lost on delete: the group memberships (what access the person had) and the account's unique ID, which logs point to. Disabling also keeps the chance to re-enable a leaver who was marked by mistake.

**Q4. Why all three proofing fields? Which one is easiest for a Scattered-Spider-style caller to fake?**
- Answer: the ID check is very important; education_verified is "either true or false".
- Grade: 0.
- Correction: each check closes a different gap; this is defence in depth. `references_contacted` is the easiest to fake, because the applicant supplies the referees' phone numbers, which an attacker with phone-social-engineering skills can control.
- AI judgement (no answer key for this question).

**Q5. Why must the requester and the approver be different people? What does this stop?**
- Answer: both accounts would have to be hacked for an approval to happen; it works like MFA.
- Grade: 1.
- Correction: the core idea, that one compromise is not enough, is right. But it needs two different people, not two factors. It stops one person, or one stolen manager account, from granting access to themselves or a friend alone.

**Q6. Why must nobody hold both `payments-initiate` and `payments-approve`? Explain the loss in money terms.**
- Answer: two accounts would need to be hacked; nobody notices the loss until the records and suspicious amounts are checked.
- Grade: 1.
- Correction: one holder can create a payment to an account they control and approve it alone. The loss is then limited only by the payment limit. Illustrative example, not a real figure: one $200,000 wire. A dishonest insider is enough; no hacking is needed.

**Q7. Why does every service account need an owner and an expiry date? What happens to an ownerless one?**
- Answer: it switches off when the owner is offline and the date has expired, so it switches off automatically.
- Grade: 1.
- Correction: an owner means someone is accountable: they attest the account and rotate its secret. Expiry forces a regular decision. In the real world, an ownerless service account usually keeps running unnoticed, with an old secret and broad access, which makes it a favourite foothold for attackers. Also, the word should be "left", not "offline".

**Q8. Why does the attestation go to the manager, not to IT?**
- Answer: a real person checks the report and outside factors such as dates; the second part: "no idea".
- Grade: 0.
- Correction: IT sees technical facts. The manager knows business facts: does this person still do payments work, have their duties changed, is a contractor's project over? Only the manager can say whether access is still needed. His quick-check answer in the walk-through was closer.

**Q9. Why is the admin password read from an environment variable? Why is a dev-only, non-secret password fine here but never in production?**
- Answer: access control; errors might expose information; "just guessing".
- Grade: 0.
- Correction: this repo is public and git history keeps everything, so a password written in a file is published. An environment variable keeps it out of the code. The dev password guards a throwaway localhost server with fake data. In production, everyone who could read the repo could log in as admin.

**Q10. Why use a fake Keycloak in unit tests, and why still keep the integration tests marked `keycloak`?**
- Answer: "absolutely no idea".
- Grade: 0.
- Correction: the fake is fast, runs anywhere, and lets us stage odd cases. But it only behaves the way we think Keycloak behaves. The real-server tests catch the places where we were wrong. Example from T3-S03: real Keycloak kept offline tokens after logout.
